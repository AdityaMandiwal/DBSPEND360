# Plan — Make "Top 5 Costliest Jobs" actually aggregate by job

Branch: `fix/top-jobs-aggregation`

## 1. Goal

Fix the "Top 5 Costliest Jobs" card on the dashboard so its data semantics match
its title: one row per `job_id`, ranked by **total** spend in the selected date
range. Today the underlying `/api/top-jobs` endpoint returns the top 5 rows of
the raw spend table (each keyed by `(cluster_id, job_id, run_id, usage_date)`),
which means a single heavy job can occupy every slot — observed live for job
`164677136540455` (ProServ Benchmark Intelligence Pipeline v2.0) where all 5
"top jobs" are the same job on different days/runs.

After this change, the card and the "Job Spending Details" table render the
same shape of data, sorted by the same metric, and cannot diverge.

## 2. Non-goals

- No changes to `/api/job-spends` (the per-row spend listing), `/api/summary`,
  or `JobSpendTable.tsx`. The per-run `JobSpend` shape stays correct as-is.
- No new business logic in the "top jobs" card — still N most expensive jobs
  by `cloud_cost + databricks_cost` in the filter window. Just the meaning of
  "job" changes from "spend-table row" to "aggregate per job_id".
- No change to the date filter, the limit parameter (default 5), or the
  pagination shape of related endpoints.
- No top-N preview of individual runs inside the card. Card stays a flat list
  of jobs. (Future enhancement; the chosen model already supports it.)

## 3. Decision: reuse `GroupedJob`, do not invent `TopJob`

Three response-model options were considered:

| Option | Verdict | Why |
|---|---|---|
| Reuse `JobSpend` | Rejected | `cluster_id`, `run_id`, `usage_date` are required on `JobSpend` and meaningful at the per-row level. After aggregation they have no meaning — we'd either populate them with sentinel values (lying about data) or mark them `Optional` (weakening the contract for the per-row listing that genuinely needs them). Frontend already displays `{job.usage_date}` on the card, which becomes wrong either way. |
| New `TopJob` model | Workable, but rejected | `TopJob` would be `GroupedJob` minus the `runs` field — same `job_id`, `job_name`, `run_count`, four cost totals, three computed properties. Duplicate definition with no semantic difference. |
| **Reuse `GroupedJob`** (chosen) | Single source of truth for "job-level aggregate". Top-5 card and Job Spending Details table speak the same model by construction; they can no longer disagree about what a job is. `runs: list[JobRun]` defaults to `[]` for the card. No new model files, no new auto-generated TS. |

The cost of reusing `GroupedJob` is a one-line docstring change — `runs` is
documented as "may be empty when the consumer only needs job-level totals".

## 5. SQL — the new `get_top_jobs()` query

Functionally identical to `get_grouped_job_spends()` but without pagination,
without the search clause, and without per-run enrichment:

```sql
WITH filtered AS (
    SELECT *
    FROM {table_name}
    WHERE usage_date >= '{start_date}'
      AND usage_date <= '{end_date}'
),
run_level AS (
    SELECT job_id, run_id,
           SUM(cloud_cost) AS cloud_cost,
           SUM(databricks_cost) AS databricks_cost,
           SUM(compute_cost) AS compute_cost,
           SUM(storage_cost) AS storage_cost,
           SUM(network_cost) AS network_cost,
           SUM(other_cost) AS other_cost
    FROM filtered
    GROUP BY job_id, run_id
),
job_level AS (
    SELECT job_id,
           SUM(cloud_cost) AS total_cloud_cost,
           SUM(databricks_cost) AS total_databricks_cost,
           SUM(compute_cost) AS total_compute_cost,
           SUM(storage_cost) AS total_storage_cost,
           SUM(network_cost) AS total_network_cost,
           SUM(other_cost) AS total_other_cost,
           COUNT(*) AS run_count
    FROM run_level
    GROUP BY job_id
)
SELECT j.job_id,
       j.total_cloud_cost,
       j.total_databricks_cost,
       j.run_count,
       lj.name,
       j.total_compute_cost,
       j.total_storage_cost,
       j.total_network_cost,
       j.total_other_cost
FROM job_level j
LEFT JOIN (
    -- Same SCD-collapse used by get_grouped_job_spends after the recent
    -- duplicate-rows fix; keeps this endpoint consistent.
    SELECT job_id, MAX_BY(name, change_time) AS name
    FROM system.lakeflow.jobs
    GROUP BY job_id
) lj ON j.job_id = lj.job_id
ORDER BY (j.total_cloud_cost + j.total_databricks_cost) DESC
LIMIT {limit}
```

### Why not factor a shared helper?

Tempting, but the two methods diverge enough (pagination + `COUNT(*) OVER()` +
search clause + per-run enrichment on the grouped path; none on the top-jobs
path) that a shared helper would mostly carry a fistful of `if` branches.
Defer until a third caller appears. The CTE shape is small and locally clear
in both places.

## 6. Slicing

Single PR. The change is tightly scoped and the backend / frontend pieces are
mutually dependent (response shape changes). Splitting into two PRs would
leave the dashboard broken between merges.

Order of work inside the PR:

1. **Backend SQL + model wiring** — rewrite `get_top_jobs()`, change router
   `response_model`. Verify via curl against the live deployment (per the
   workspace's FastAPI verification protocol) that the new response shape
   matches `GroupedJob` and that the first row is the correct top job.
2. **Regenerate TS client** — `./watch.sh` does this automatically on backend
   restart; otherwise `uv run scripts/make_fastapi_client.py`. Verify the
   generated `DashboardService.ts` now returns `Array<GroupedJob>`.
3. **Frontend rewire** — update `api-client.ts`, `useJobSpends.ts`,
   `SummaryCards.tsx`. TypeScript will flag every site that referenced the
   removed `run_id` / `usage_date` / `cluster_id` fields — fix those.
4. **Extend dedup test** — add the second assertion to
   `claude_scripts/test_job_spend_dedup.py`.
5. **Deploy + monitor** — `./deploy.sh`, then `dba_logz.py` for uvicorn
   startup, then `dba_client.py /api/top-jobs?...` to spot-check the card's
   underlying data.

Each step is verifiable without committing to the next, so we can stop and
reassess if anything looks off.

## 7. Acceptance criteria

1. `GET /api/top-jobs?start_date=...&end_date=...&limit=5` returns a JSON
   array of exactly N (or fewer, if the workspace has fewer than N billed
   jobs) objects, each conforming to the `GroupedJob` schema with `runs: []`.
2. Every returned object has a distinct `job_id`. No two entries share an id.
3. For any window where the response is non-empty, the first entry's
   `total_cost` equals the maximum of `total_cloud_cost + total_databricks_cost`
   across all jobs in `/api/grouped-job-spends` for the same window. (i.e. the
   card's #1 entry matches the table's #1 row.)
4. Each entry's `total_cost` is monotonically non-increasing through the
   array (ordering preserved).
5. The card on the dashboard renders five distinct job names for any window
   that has five or more jobs with spend in the workspace. For the live
   workspace's 2026-04-29 → 2026-05-29 window, the top job is ProServ
   Benchmark Intelligence Pipeline v2.0 with one entry, not five.
6. Each card row displays `run_count` (e.g. "12 runs") in the secondary line
   instead of `usage_date`.
7. The "Job Spending Details" table is unchanged (same data, same shape).
   `/api/grouped-job-spends`, `/api/job-spends`, `/api/summary` regressions:
   none.
8. `claude_scripts/test_job_spend_dedup.py` exits with code 0; the new
   top-jobs assertion is exercised.
9. Deployed app log stream shows `Application startup complete.` /
   `Uvicorn running` with no exceptions; live curl checks against
   `/api/top-jobs` and `/api/grouped-job-spends` agree on the #1 job and its
   total cost.

## 8. Risks & mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| Existing callers of `getTopJobs()` rely on `run_id` / `cluster_id` / `usage_date` | Low — `Grep` shows the only caller is `SummaryCards.tsx`, which only reads `job_id`, `job_name`, `total_cost`, `usage_date`. | TypeScript will fail to compile if any other reference exists. We catch this at build time, not in production. |
| `GroupedJob` carrying `runs: []` confuses future readers | Low | One-line docstring update on the model + a code comment in `get_top_jobs()` explaining why `runs` is intentionally empty here. |
| Query performance — the new top-jobs query is heavier than a `SELECT … ORDER BY … LIMIT 5` | Low — `get_grouped_job_spends()` runs the same CTE chain and is fast enough in practice. Top-jobs doesn't do the `COUNT(*) OVER()` window, so it should be slightly cheaper than grouped. | Monitor uvicorn log timestamps on first deploy. If we see a regression > 2× the old endpoint, revisit. |
| Stale React Query cache shows old shape briefly after deploy | Negligible — `staleTime: 5 min`, but the TS types change so a stale-cache render would already be a type error during build. | None needed; users will see fresh data on next page load after deploy. |

## 9. Rollback

The change is fully contained to one branch and ships in a single deploy. If
the deploy is bad:

- Revert the merge commit on `main`.
- Redeploy via `./deploy.sh`.
- Previous behaviour (broken-but-stable per-row "top 5") is restored.

No data migrations, no schema changes, no irreversible state. Safe.
